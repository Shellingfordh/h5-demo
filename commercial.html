15 · JAVA 27

Java 27：真正值得 AI 后端讨论的，不是新语法，而是密度、GC、安全和长期工程

Compact Object Headers 默认启用

96 → 64 bit
64 位架构对象头缩小，有利于降低堆占用、提升部署密度和数据局部性。对大量短生命周期对象、JSON/事件/Agent 状态的服务值得观察。

G1 在所有环境成为默认 GC

讨论点不是“G1 好不好”，而是：AI Orchestration 服务大量 I/O + 大量中间对象时，团队有没有真实 GC 监控、JFR 和容量基线？

Post-Quantum Hybrid TLS

JDK 27 加入 TLS 1.3 后量子混合密钥交换方向，对长期企业/设备通信安全有现实意义。
现场问题：如果我们今天从零做“设备 + Agent + 企业后台”，团队会直接上 JDK 27，还是坚持 JDK 25 LTS？你们判断“最新版本可用”的标准是什么：框架、GC、供应商支持、线上经验还是安全周期？
来源：Oracle JDK 27 Release Notes（2026-09 / 10）16

17 · RUST 1.99

Rust 1.99：如果公司要碰硬件和端侧，Rust 的问题已经不是“酷不酷”，而是值不值得建立能力

1.99：定义 C ABI variadic functions 稳定

Rust 不只是调用 C 的可变参数函数，现在可以直接定义 C / C-unwind ABI variadic functions。对系统集成、既有 C 生态和 FFI 边界更友好。

Raw pointer layout APIs

继续补齐底层内存布局能力，适合讨论 Runtime、驱动周边、端侧库。

1.99.1：FFI bool x86_64 修复

10 月 15 日点版本修复了 x86_64 FFI `bool` 返回值可能违反 ABI 预期的问题，也修复部分 UEFI / macOS 链接回归。
现场问题：我们如果做 AI 眼镜 / 可穿戴，Rust 应该放在设备侧、跨平台 SDK、推理 Runtime 周边，还是完全没必要？引入 Rust 后谁维护、怎么和 Java/Go 协作？
来源：Rust 官方 1.99.0 / 1.99.1 Release Announcements18
18 · STACK TRADE-OFF

Java / Go / Rust：不是排名，是边界设计

内部讨论用主观雷达，不是 benchmark：蓝=Java，绿=Go，黄=Rust。

建议边界

Java：核心业务、账号/订单/企业系统、复杂领域逻辑。

Go：AI Gateway、工具编排、SSE/WebSocket、任务中间层、云服务。

Rust：设备侧/SDK/性能敏感组件、跨平台库、FFI、端侧 Runtime 周边。
真正要问开发：如果团队现在 90% 是 Java，这套边界值得引入两门语言吗？什么业务量、性能瓶颈或硬件需求出现时，收益才超过组织复杂度？
语言选型的最终指标：交付速度 × 可靠性 × 单位成本 × 可维护性19

如果公司只能押一个 18 个月方向：AI 眼镜应用、健康可穿戴、世界模型、企业 Agent，你押哪个？为什么另外三个不押？
02

商业闭环

三个月必须出现第一笔真实收入：你选订阅、硬件、企业项目、交易佣金中的哪一种？第一版砍掉什么？
03

壁垒

底层模型六个月后全部变强、变便宜，你今天做的产品还剩什么？数据、分发、硬件、工作流还是关系链？
真正强的产品，不是把每个方向都说“有机会”，而是敢于解释：为什么现在只做这个，以及什么数据出现时我会承认自己错了。
讨论目的：判断团队有没有“选择与收敛”能力24
24 · ENGINEERING DISCUSSION

给开发的五个讨论题：全部围绕最新版本 + 真实边界

① Java 27 vs JDK 25 LTS：新项目为什么选一个而不是另一个？你们的升级门槛是什么？

② Go 1.27：generic methods / json/v2 / goroutine leak profile，哪些会改变真实生产代码？

③ Rust 1.99：AI 硬件项目里，Rust 的引入点在哪里才值得组织成本？
④ 跨语言边界：Java 核心业务 + Go Agent Gateway + Rust 端侧 SDK，会不会把排障复杂度放大到不值得？

⑤ AI Coding：如果 Agent 能把陌生语言的 70% 初稿写出来，你们如何定义“可以上生产”？测试、Review、性能、SLO 谁负责？
观察点：不要只听“能不能做”。听他是否主动谈兼容性、部署、GC/内存、可观测性、故障域、CI、回滚、FFI、团队 ownership 和长期维护。
目的不是考八股，而是了解真实工程成熟度25
25 · HARDWARE DISCUSSION

给硬件团队：我们最需要知道的不是“会不会做”，而是哪里会卡死周期

端云边界

眼镜/戒指什么数据本地处理？什么上传？断网、隐私、延迟怎么兜底？

功耗与热

持续音频、摄像头、显示、无线、端侧模型一起开时，真正预算怎么分？

BOM 与订阅

多 100 元硬件成本，能否换来每年更高云成本节省或更高订阅转化？

SDK / OTA

如果我们先做应用层，硬件厂商能开放到什么程度？协议和 OTA 谁掌控？

数据质量

健康传感器、视觉输入、麦克风的真实噪声会怎样影响 AI 结果？

量产周期

软件被 AI 压快以后，打板、认证、供应链、测试会不会成为新的关键路径？
硬件商业化 = 体验 × BOM × 功耗 × 供应链 × 软件持续收入26
26 · RECOMMENDATION

我的建议：现在就给一个小队、一个周期，押“AI 新终端 Agent 应用层”

为什么现在

✓ 北京政策明确支持智能眼镜、Agent、世界模型
✓ 智能眼镜销量与政策同时升温，但应用层仍未定型
✓ 可穿戴健康正在从“监测”走向“数据 + AI 服务”
✓ 世界模型刚进入更强实时交互阶段
✓ AI Coding 让小团队跨语言、跨项目验证的成本继续下降

我们先做什么

1. 选择 2—3 个眼镜/可穿戴高频 Agent 场景
2. 先做跨硬件应用层，不先背整机风险
3. 建统一记忆、工具调用、设备事件、成本与日志底座
4. 同时做一个世界模型应用 PoC，作为中长期储备
5. 12 周内用真实用户和第一笔收入决定 Scale / Kill
我们不是要证明“AI 很有前景”。这件事已经不需要证明。我们要证明的是：公司能不能在这个窗口期形成自己的主营产品，而不是永远做一堆零散互联网需求。
要资源的理由：窗口期 + 可复用能力 + 明确阶段验证27
